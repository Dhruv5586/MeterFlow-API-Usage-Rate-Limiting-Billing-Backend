# MeterFlow Database Design

## Scope and design principles

This design covers the ten Phase 1 PostgreSQL tables. It does not create API
routes or implement authentication, billing workflows, or a frontend.

- Use UUID primary keys for independently created records. PostgreSQL's
  `gen_random_uuid()` supplies IDs by default.
- Use `TIMESTAMPTZ` for instants. Source log timestamps do not include a
  timezone, so ingestion must use an explicitly agreed timezone rather than
  pretending the source specifies one.
- Use `NUMERIC` for prices and invoice amounts; binary floating-point is not
  suitable for exact currency arithmetic.
- Store password hashes and keyed hashes of API key secrets, never plaintext
  credentials. The key prefix can be displayed to help a developer identify a
  key; it must not reveal the secret.
- Do not persist raw IP addresses, user agents, or referrers from the source
  logs. They are unnecessary for usage billing and may identify people.
- Keep `usage_events` as the detailed ledger. `usage_daily` is a rebuildable
  summary for fast reporting.
- Retain invoices, usage, and audit history. Use `RESTRICT` on core references
  rather than deleting financial history when a user, plan, or key is removed.
  Prefer status/revocation changes or a documented retention process.

The schema targets PostgreSQL 13 or later for built-in `gen_random_uuid()`.
`UUID`, `JSONB`, partial indexes, and `TIMESTAMPTZ` are PostgreSQL types or
features, not JavaScript data types.

## Tables

`PK` means primary key, `FK` foreign key, `UQ` unique constraint/index, `NN`
NOT NULL, and `CK` check constraint. Unless shown nullable, columns are `NN`.
Each UUID `id` is a primary key with `DEFAULT gen_random_uuid()`.

### 1. `users`

**Purpose:** The MeterFlow developer/customer account.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK; generated by PostgreSQL. |
| `email` | TEXT | NN, UQ; CK nonempty and lowercase; normalize before insert. |
| `password_hash` | TEXT | NN; password hash only, never a password. |
| `display_name` | TEXT | NN. |
| `status` | TEXT | NN, default `active`; CK in `active`, `suspended`, `closed`. |
| `created_at`, `updated_at` | TIMESTAMPTZ | NN, default current time. |

No separate profile table is required for Phase 1. Email is unique because it
identifies an account for sign-in and communication.

### 2. `api_keys`

**Purpose:** Stores the verification material and lifecycle for a developer's
API credentials.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `user_id` | UUID | NN, FK to `users.id`, `ON DELETE RESTRICT`. |
| `name` | TEXT | NN; CK nonempty; user-provided label. |
| `key_prefix` | TEXT | NN; CK nonempty; non-secret display prefix. |
| `key_hash` | CHAR(64) | NN, UQ; CK for 64 lowercase hexadecimal characters; HMAC-SHA-256 digest of the high-entropy secret, keyed using an application secret held outside the database. |
| `created_at` | TIMESTAMPTZ | NN, default current time. |
| `expires_at`, `revoked_at`, `last_used_at` | TIMESTAMPTZ | Nullable; key lifecycle timestamps. |

CK: `expires_at` must be later than `created_at` when present. CK: `revoked_at`
must not precede `created_at` when present. A user has many keys; a key belongs
to exactly one user. Revoke a key rather than deleting it if its history is
needed. Raw key material is returned only at creation and is not recoverable
from this table. UQ on `(user_id, id)` is also declared so composite foreign
keys can enforce key ownership for events and daily aggregates.

### 3. `subscription_plans`

**Purpose:** Defines catalog entries and prices that subscriptions select.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `code` | TEXT | NN, UQ; CK nonempty; stable code such as `free`, `pro`, or `enterprise`. |
| `name` | TEXT | NN. |
| `price` | NUMERIC(12,2) | NN, CK >= 0; price for the selected billing interval. |
| `currency` | CHAR(3) | NN, default `USD`; CK for three uppercase letters. |
| `billing_interval` | TEXT | NN; CK in `month`, `year`. |
| `is_active` | BOOLEAN | NN, default true; inactive plans cannot be newly selected. |
| `created_at` | TIMESTAMPTZ | NN, default current time. |

Plan identity and price live here; subscription-specific dates and status live
in `subscriptions`. A plan has zero or many historical subscriptions.

### 4. `subscriptions`

**Purpose:** Records which plan a user is on and the lifecycle/billing period
for that selection.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `user_id` | UUID | NN, FK to `users.id`, `ON DELETE RESTRICT`. |
| `plan_id` | UUID | NN, FK to `subscription_plans.id`, `ON DELETE RESTRICT`. |
| `status` | TEXT | NN; CK in `trialing`, `active`, `past_due`, `canceled`, `ended`. |
| `starts_at` | TIMESTAMPTZ | NN. |
| `current_period_start`, `current_period_end` | TIMESTAMPTZ | NN; CK end is later than start. |
| `canceled_at` | TIMESTAMPTZ | Nullable. |
| `cancel_at_period_end` | BOOLEAN | NN, default false. |
| `created_at` | TIMESTAMPTZ | NN, default current time. |

A user and a plan can be linked many times over time; `subscriptions` is the
associative record for that many-to-many history. A partial unique index should
permit at most one current subscription per user (statuses `trialing`, `active`,
or `past_due`) while retaining ended subscriptions. Usage events reference the
subscription that was in force for their accounting. UQ on `(user_id, id)`
supports composite FKs that verify ownership of related events and invoices.

### 5. `usage_events`

**Purpose:** Append-oriented request ledger used for usage accounting,
investigation, and rebuilding aggregates.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `user_id` | UUID | NN, FK to `users.id`, `ON DELETE RESTRICT`. |
| `api_key_id` | UUID | NN; composite FK with `user_id` to `api_keys(user_id, id)`, `ON DELETE RESTRICT`. |
| `subscription_id` | UUID | NN; composite FK with `user_id` to `subscriptions(user_id, id)`, `ON DELETE RESTRICT`. |
| `http_method` | TEXT | NN; CK in `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`. |
| `endpoint` | TEXT | NN; CK nonempty and begins with `/`; normalized path without query string. |
| `status_code` | SMALLINT | NN; CK from 100 through 599. |
| `latency_ms` | INTEGER | NN; CK >= 0. |
| `response_size_bytes` | BIGINT | NN; CK >= 0. |
| `source_server_id` | TEXT | Nullable; source system's server identifier, not a MeterFlow identity. |
| `source_record_key` | TEXT | Nullable, UQ; stable idempotency key for an imported row. |
| `created_at` | TIMESTAMPTZ | NN; event time, not necessarily insertion time. |

In addition to the user FK, composite FKs `(user_id, api_key_id)` and
`(user_id, subscription_id)` reference `(user_id, id)` on `api_keys` and
`subscriptions`. This makes PostgreSQL reject a key or subscription owned by
some other user. Never invent IDs to satisfy a foreign key. `source_record_key`
allows retries of the same source row without creating duplicate imported
events; a unique constraint permits multiple `NULL` values for non-imported
events.

The CSV has no user/key identifiers, so its rows cannot currently be assigned
to seeded identities without an explicit deterministic mapping. Import must
not start until attribution and timestamp timezone rules are approved.

### 6. `usage_daily`

**Purpose:** Stores daily request totals for fast quota and usage reports. It
is derived from `usage_events` and can be rebuilt.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `user_id` | UUID | NN, FK to `users.id`, `ON DELETE RESTRICT`. |
| `subscription_id` | UUID | NN; composite FK with `user_id` to `subscriptions(user_id, id)`, `ON DELETE RESTRICT`. |
| `api_key_id` | UUID | NN; composite FK with `user_id` to `api_keys(user_id, id)`, `ON DELETE RESTRICT`. |
| `usage_date` | DATE | NN; UTC calendar date for event aggregation. |
| `endpoint` | TEXT | NN; normalized endpoint dimension. |
| `http_method` | TEXT | NN; method dimension. |
| `request_count` | BIGINT | NN, CK >= 0. |
| `successful_request_count`, `error_request_count` | BIGINT | NN, default 0, each CK >= 0. |
| `response_bytes`, `latency_sum_ms` | BIGINT | NN, default 0, each CK >= 0. |
| `updated_at` | TIMESTAMPTZ | NN, default current time. |

UQ on `(usage_date, subscription_id, api_key_id, endpoint, http_method)` keeps
one aggregate for each dimension. The summary intentionally duplicates
calculated totals from events; it is controlled, derived denormalization for
read speed, not an independent source of truth. `successful` means status 200
through 399; `error` means 400 through 599. Informational 1xx responses are
neither of those categories. CK that the sum of `successful_request_count` and
`error_request_count` is at most `request_count`; the remaining count, if any,
represents informational responses.

### 7. `usage_quotas`

**Purpose:** Defines the usage limits granted to a particular subscription.
Snapshotting quota rows per subscription preserves the entitlement even if a
plan's catalog settings later change.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `subscription_id` | UUID | NN, FK to `subscriptions.id`, `ON DELETE RESTRICT`. |
| `metric` | TEXT | NN; e.g. `requests`. |
| `period` | TEXT | NN; CK in `day`, `month`. |
| `quota_limit` | BIGINT | NN, CK >= 0. |
| `is_hard_limit` | BOOLEAN | NN, default false. |
| `created_at`, `updated_at` | TIMESTAMPTZ | NN, default current time. |

UQ on `(subscription_id, metric, period)` prevents conflicting duplicate quota
definitions. A subscription has zero or many quota dimensions.

### 8. `invoices`

**Purpose:** Stores a bill-to-user snapshot for a subscription billing period.
Amounts use fixed-precision decimal arithmetic.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `user_id` | UUID | NN, FK to `users.id`, `ON DELETE RESTRICT`. |
| `subscription_id` | UUID | NN, composite FK with `user_id` to `subscriptions(user_id, id)`, `ON DELETE RESTRICT`. |
| `invoice_number` | TEXT | NN, UQ; externally readable business identifier. |
| `status` | TEXT | NN; CK in `draft`, `open`, `paid`, `void`, `uncollectible`. |
| `currency` | CHAR(3) | NN; CK for three uppercase letters. |
| `subtotal`, `tax`, `total` | NUMERIC(12,2) | NN; each CK >= 0. |
| `issued_at`, `due_at`, `paid_at` | TIMESTAMPTZ | `issued_at` NN; others nullable; CK `due_at >= issued_at` when due date exists. |
| `created_at` | TIMESTAMPTZ | NN, default current time. |

A subscription can have many invoices; each invoice belongs to one user and
one subscription. The composite FK ensures the user matches the subscription
owner.

### 9. `invoice_items`

**Purpose:** Explains individual plan, overage, or adjustment lines on an
invoice.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `invoice_id` | UUID | NN, FK to `invoices.id`, `ON DELETE CASCADE`. |
| `description` | TEXT | NN; human-readable line description/snapshot. |
| `quantity` | NUMERIC(14,4) | NN, CK >= 0. |
| `unit_price` | NUMERIC(12,4) | NN, CK >= 0. |
| `line_amount` | NUMERIC(12,2) | NN, CK >= 0; rounded amount stored for the invoice. |
| `created_at` | TIMESTAMPTZ | NN, default current time. |

Deleting a draft invoice may cascade its lines. Issued invoices should be
retained, not deleted. Invoice totals are stored snapshots; database row-level
checks cannot enforce that `total` equals the sum of child rows, so invoice
creation must calculate and validate this inside one transaction.

### 10. `audit_logs`

**Purpose:** Records security- and billing-relevant actions for traceability.

| Column | Type | Constraints and meaning |
| --- | --- | --- |
| `id` | UUID | PK. |
| `actor_user_id` | UUID | Nullable FK to `users.id`, `ON DELETE SET NULL`; null for system actors or retained records after account deletion. |
| `action` | TEXT | NN; CK nonempty action name. |
| `entity_type` | TEXT | NN; CK nonempty affected entity type. |
| `entity_id` | UUID | Nullable; affected row ID (polymorphic, so no direct FK). |
| `details` | JSONB | NN, default empty object; CK that value is a JSON object; allowlisted non-secret metadata only. |
| `occurred_at` | TIMESTAMPTZ | NN, default current time. |

No raw API secrets, password material, raw IP addresses, or unnecessary request
payloads belong in `details`. A polymorphic `entity_id` cannot be enforced as a
normal FK; the action-writing code must ensure it refers to the intended entity.

## Relationships and deletion rules

| Relationship | Cardinality | Deletion behavior |
| --- | --- | --- |
| User → API keys | One-to-many | Restrict physical user deletion while keys remain; revoke keys instead. |
| User → subscriptions | One-to-many | Restrict; retain history. |
| Plan → subscriptions | One-to-many | Restrict; deactivate plans instead of deleting referenced plans. |
| User ↔ plan, through subscriptions | Many-to-many over time | `subscriptions` records the relationship and its lifecycle. |
| User/key/subscription → usage events | One-to-many each | Restrict; retain the usage ledger. |
| Subscription/key → daily aggregates | One-to-many each | Restrict; aggregates are rebuildable but tied to retained identities. |
| Subscription → quotas | One-to-many | Restrict; preserve entitlement history. |
| User/subscription → invoices | One-to-many each | Restrict; retain billing records. |
| Invoice → invoice items | One-to-many | Cascade only for draft/transactional cleanup; issued invoices are retained. |
| User → audit logs as actor | One-to-many, actor optional | Set actor FK to NULL when user is physically deleted; preserve audit event. |

There is no natural one-to-one relationship among these ten tables, so none is
forced artificially. `subscriptions` is the associative entity for the
user/plan many-to-many history.

## Normalization

- **First Normal Form (1NF):** Each column holds one value, with no repeating
  lists. For example, each API key is its own row rather than a comma-separated
  list on `users`.
- **Second Normal Form (2NF):** Non-key facts depend on the whole key. The
  plan's price belongs in `subscription_plans`, not in a subscription's
  identity; the daily aggregate dimensions have one unique dimension key and
  totals for that whole combination.
- **Third Normal Form (3NF):** Non-key facts depend on that table's key, not on
  another non-key fact. User email/password data stays in `users`; plan facts
  stay in `subscription_plans`; invoice line descriptions and prices are
  snapshots on `invoice_items`. Usage aggregates are the deliberate exception
  to strict non-duplication: they are computed summaries, clearly marked as
  rebuildable rather than canonical facts.

## Integrity and transactions

Primary keys uniquely identify rows. Foreign keys prevent references to
nonexistent users, subscriptions, plans, keys, or invoices. Composite foreign
keys additionally prevent a valid ID from being paired with another user's
identity. Unique constraints
protect natural identifiers such as normalized email, plan code, key digest,
invoice number, and daily aggregate dimensions. `NOT NULL` and `CHECK`
constraints reject incomplete or nonsensical data (negative latency, invalid
status ranges, negative monetary amounts, and inverted time periods).

The composite ownership FKs on events, daily summaries, and invoices enforce
that a key or subscription belongs to the supplied user, including for direct
SQL writes.

An importer should batch a set of events in a transaction and use
`source_record_key` uniqueness with `ON CONFLICT` handling for retries. Seed
operations should insert parent rows before children, or insert related rows
within one transaction. Do not treat a partially committed import as success.

`database/seed.sql` uses `pgcrypto` to create bcrypt password hashes from
discarded random values and HMAC API-key hashes from discarded random bytes.
Those 50 API-key rows are marked revoked; neither credentials nor HMAC
secrets are stored or printed, so the seed keys cannot authenticate. They are
relationship/test fixtures, not developer-issued credentials. The seed uses
stable IDs and `ON CONFLICT (id) DO NOTHING` so rerunning it does not overwrite
existing sample rows. It creates 50 developers (20 Free, 20 Pro, 10
Enterprise) and one daily request quota per subscription.

## Index and query strategy

The primary-key and unique constraints create indexes automatically; do not
add duplicate indexes over the same columns. Planned workload indexes belong
in `database/indexes.sql` and should cover:

- Key and subscription management: `(user_id, created_at DESC)`.
- Recent events for a user, API key, or subscription: identity followed by
  descending `created_at`.
- Daily summaries by subscription or API key: identity followed by descending
  `usage_date`; the unique aggregate-dimensions constraint serves inserts and
  exact-dimension lookups.
- Invoice history by user or subscription: identity followed by descending
  `issued_at`; invoice-item lookup by `invoice_id`.
- Audit history by actor and occurrence time, excluding system actors with a
  partial index.

A partial unique index on `subscriptions(user_id)` for current statuses enforces
one current subscription per user without blocking historical rows. Confirm
every proposed index against real queries with `EXPLAIN (ANALYZE, BUFFERS)` on
representative data; `ANALYZE` executes the query, so use care with expensive
statements. Compare query plans and timings before/after an index when the
database and representative dataset are available. PostgreSQL tooling/server
is unavailable in the current environment, so no measured performance claim is
made.

`daily_api_usage` exposes the stored daily dimensions and counts, including
average latency (null when there are no requests). `subscription_usage_summary`
rolls those summaries up across all recorded dates for each subscription; it
is a lifetime total, not a current billing-period quota calculation. Use the
daily view with an explicit date range for period-specific reports.

## Demo Users and API Keys (Step 3 Implementation)

### 1. Why Demo Users Are Required
Raw access logs (such as `access_logs.csv`) contain only transport metadata: IP addresses, request paths, status codes, and server IDs. They do not contain application tenant entities such as `user_id`, `api_key_id`, or `subscription_id`.

To fulfill the strict foreign-key integrity constraints in PostgreSQL without inventing dangling or orphaned records:
- MeterFlow provisions realistic, persistent demo tenant accounts.
- These accounts represent realistic developer personas across different plan tiers (Free, Pro, Enterprise).
- Each demo account has deterministic UUIDs so scripts and subsequent ingestion passes can reliably refer to them.

### 2. How API Keys Are Associated With Users
The schema enforces tenant ownership via:
- Primary foreign key: `api_keys.user_id REFERENCES users(id) ON DELETE RESTRICT`.
- Composite unique key: `UNIQUE (user_id, id)`.
- Event-level composite foreign key: `usage_events(user_id, api_key_id) REFERENCES api_keys(user_id, id)`.

This database architecture makes it impossible for an event or usage ledger entry to attribute usage to an API key owned by a different user.

### 3. How API-Key Hashes Are Stored
To protect credentials against database dumps or unauthorized inspection:
- High-entropy secrets are generated using Python's `secrets.token_urlsafe(32)`.
- The secret format is `mf_live_<random_bytes>`.
- The database stores **only** a 64-character lowercase SHA-256 hexadecimal digest (`key_hash`).
- PostgreSQL enforces this format via `CONSTRAINT api_keys_hash_format_ck CHECK (key_hash ~ '^[0-9a-f]{64}$')`.
- A non-secret prefix (e.g. `mf_live_a1b2c3d4`) is stored in `key_prefix` for UI display and audit identification.
- Plaintext keys are shown only once at creation time and are never stored or logged.

### 4. How These IDs Will Be Used When Importing CSV Usage Events
During CSV ingestion (Step 6 / Phase 1 dataset transformation):
- Log entries are mapped deterministically or distributed among the demo users and their respective API keys and subscriptions.
- Each imported `usage_event` row receives:
  - `user_id`: e.g. `20000000-0000-4000-8000-000000000001` (TechNova Solutions)
  - `api_key_id`: e.g. `40000000-0000-4000-8000-000000000001`
  - `subscription_id`: e.g. `30000000-0000-4000-8000-000000000001`
- This ensures full referential integrity and enables accurate per-user quota and billing metrics.

## Step 4 Implementation: Batch Ingestion & Deduplication Architecture

### 1. Unique Constraints & Duplicate Prevention
To guarantee idempotent ingestion and protect against duplicate billing:
- Each imported CSV record possesses a deterministic source key: `source_record_key = f"access_logs_csv:{source_record_id}"`.
- PostgreSQL enforces uniqueness on `usage_events.source_record_key`.
- Ingestion queries use:
  ```sql
  INSERT INTO usage_events (...)
  VALUES (...)
  ON CONFLICT (source_record_key) DO NOTHING;
  ```
- Any re-run of the import process automatically skips already-ingested records without throwing runtime errors or creating duplicate billing entries.

### 2. Transactional Batch Insertion
- Records are loaded in configurable chunks of 100 rows per transaction.
- If a database failure or network disconnect occurs mid-batch, PostgreSQL automatically rolls back that specific batch, ensuring the database ledger is never left in a corrupt or partially written state.

### 3. Referential Validation
- Before batch execution, `scripts/import_usage_events.py` queries the database for all valid `(user_id, api_key_id, subscription_id)` triplets.
- Any event not matching a valid, active user-key pair is rejected prior to sending SQL statements, safeguarding foreign-key integrity.
